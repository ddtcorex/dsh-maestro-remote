## Purpose

Remote-access / tunneling plugin for the DeepSeek Harness (DSH): exposes a cloudflared tunnel + remote proxy so a DSH session can be reached remotely, with PIN auth and, when the optional `dsh-maestro-notifier` plugin is present, startup notifications.

Names by boundary: npm package = `@ddtcorex/dsh-maestro-remote`; three Cordis patch rows in `cordis.patch.yml`: `dsh-maestro-remote-rpc` (channel `/dsh-maestro-remote`), `dsh-maestro-tunnel` and `maestro-patch`. This package absorbed `dsh-maestro-patch`. It registers no tools (`ctx.tools.register` is never called); its surface is the `maestroTunnel` service, the RPC channel and the settings section.

Part of the Maestro Harness suite. Host half + client half (settings/slot UI).

## Layout

- `src/host/index.ts`: host `apply()`: wires tunnel + proxy + RPC (no tools).
- `src/host/tunnel.ts` — cloudflared tunnel lifecycle (start/stop/status, reversible via `ctx.effect`).
- `src/host/remote-proxy.ts` — the remote proxy handler.
- `src/host/cloudflared-fetch.ts` — fetches/installs the `cloudflared` binary.
- `src/host/startup-notify.ts` — schedules the protected "DSH web is ready" update via the optional
  `maestroNotifier` service (published by `@ddtcorex/dsh-maestro-notifier`); transport only — the
  message text stays here, delivery goes through the pluggable provider registry.
- `src/host/pin-store.ts`: reads and rotates the PIN and the LAN PIN, stored as files under `~/.dsh/dsh-maestro-remote/` (`pin`, with the legacy `token` and `token-lan` files as fallbacks); `src/host/secure-compare.ts` — constant-time comparison.
- `src/host/config-store.ts`: flat `MaestroUserConfig` adapter over the embedded store, plus the runtime sidecar for `lastTunnelRunning`.
- `src/host/vendor/store.ts`: committed, hash-sealed copy of `dsh-maestro-core`'s settings store (generated by core's `scripts/vendor-store.mjs`; do not hand-edit). The shared document is `~/.dsh/dsh-maestro-config/settings.json`.
- `src/host/rpc.ts`: loopback RPC on `/dsh-maestro-remote`: the tunnel, proxy, PIN and config endpoints (`maestro.tunnelStart`, `maestro.tunnelStop`, `maestro.getPin`, `maestro.rotatePin`, `maestro.lanPin.*`, `maestro.getConfig`, `maestro.saveConfig`, ...).
- `src/host/access-log.ts`: size-rotated diagnostic access log of the remote proxy under `~/.dsh/dsh-maestro-remote/logs/`.
- `src/host/tunnel-watchdog.ts`: backoff retry policy that keeps restarting the tunnel while `lastTunnelRunning` is set.
- `src/host/serialized-writes.ts`: serializes the `lastTunnelRunning` writes so `start()` and `stop()` cannot interleave.
- `src/host/patch/` and `src/client/patch/`: the `maestro-patch` row (viewport, apple-touch-icon, connection loopback, welcome), absorbed from `dsh-maestro-patch`. It stays its own row so the patches work with the tunnel off.
- `src/client/index.tsx` + `src/client/remote/`: the `maestro-remote` settings section (id `maestro-remote`, order 31): Tunnel and LAN.
- `src/host/augment.d.ts` — local structural types (do NOT import from `deepseek-harness`).
- `tests/remote.test.ts` + `tests/startup-notify.test.ts` — vitest suites.

- One TDD task = one commit; never commit while `pnpm verify` is red.
- **Always request approval before merge or release:** never merge a PR/MR or publish a release (`git tag`/`pnpm publish`/`gh release`) without an explicit human approval — request review (`gh pr ready` / `gh pr request-review` / ask in chat) and wait for `APPROVED`. This applies to every `master` merge and every `vX.Y.Z` tag (see `docs/PUBLIC_REPO_CHECKLIST.md` §2/§8).

## Conventions

- **Secrets** — compare PINs/tokens with `secure-compare.ts` (constant-time); never log or echo a PIN/token. No real tokens in tests or fixtures.
- **Tunnel lifecycle** — every process/socket/timer must be reversible: register in `ctx.effect(...)` and return a disposer that tears the tunnel down.
- **Host/client split** — network + process work in the host; the client only renders status/settings via slots and calls host RPC with lossless JSON.
- Keep the config/pin storage consistent with the other `dsh-maestro-*` packages (same layout/atomic-store conventions).

## Validation

`pnpm verify` + `pnpm test` green before any success claim. Run `pnpm build` before `pnpm test` on a clean tree: `tests/client-loader-id.spec.ts` and `tests/row-addressing.spec.ts` read `lib/` and fail without it (verified on master, not caused by any recent change). A tunnel feature must be validated live (a real tunnel start/stop + proxy round-trip), not just via unit tests.
